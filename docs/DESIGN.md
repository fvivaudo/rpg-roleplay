# Nekron — 2D Web-Based Cyberpunk MMO: Full Design & Implementation Plan

## Context

Nekron is a 2D web-based cyberpunk roleplay MMO in the lineage of **Dreadcast** (https://www.dreadcast.net/ — the declared reference for overall feel): a central map window the player moves across in deliberate steps, a highly interactive location-based chat as the true centerpiece, uploaded-avatar identity, paper-doll equipment, and a player-driven RP society. The world spans multiple player-founded cities over a procedurally seeded world map, with building interiors and vertical levels joined by stairs and elevators, transports that are themselves playable spaces, turn-based combat on the live map, death that leads to a playable Limbo, a trait system that makes every character mechanically unique, an economy whose main money sink is the live-ops content pipeline itself, private instancing for events, and a three-tier editor ecosystem (GM world editor, player building editor, GM dungeon/POI editor).

The existing repo is an early prototype (a Bun-workspaces monorepo, `client` + `server`, single `main` branch). This plan treats it as reference material and reworks the architecture. All decisions below were settled feature-by-feature in conversation with Florian; remaining tuning/content questions are listed at the end. **This document is the deliverable — execution comes later.**

### Current state (re-surveyed 2026-07-17)

Phase 0 is done, and a **V0 vertical slice** shipped beyond it, browser-verified end-to-end: register → create character → move on a map → edit and save a level → forum thread/reply.

- `server`: Bun + Elysia 1.2 + **Drizzle** (Prisma removed) + Postgres (Neon live via `server/.env`; docker-compose Postgres for the verification loop). Auth complete — login/signup/refresh/logout/`/me`, bcrypt, httpOnly-cookie access+refresh JWTs with `exp` claims; response bodies never carry tokens or the password hash. Routes split per domain (`auth`, `characters`, `maps`, `forum`); idempotent boot seed (starter map + forum categories). Nine tables: `User`, `Character` (jsonb attributes), `Map`/`MapLevel`/`MapLevelRevision`, `ForumCategory/Thread/Post`, plus the legacy `ChatMessage` from the old broadcast-WS prototype (superseded by Part V's two-table design in Phase 2). Level saves run the Part X pipeline (validate → version bump → revision → touch map) and are **Admin-gated**. The 2026-07 Supabase credential leak is resolved: creds rotated, history purged and force-pushed.
- `client`: lean Vite + React 18 + Excalibur 0.30 shell (bulletproof-react scaffold deleted). Live routes: game (Excalibur renders `LevelData`, click-to-move via shared `findPath` — **client-local**, replaced by server-authoritative rooms in Phase 1), characters (point-buy creation), editor (DOM-grid, saving through the real pipeline), forum. Tile atlas vendored at `client/public/game/tileset.png`.
- `packages/protocol` (shared entity + game types: RACES with size ranges and attribute mods, point-buy constants, the `LevelData` format) and `packages/world` (grid/level/character pure functions, `bun test`ed) are live; the server re-validates character creation with the same functions the UI uses.

## Part I — Foundational decisions

**Incremental rework** on the existing Bun workspaces monorepo, extended with shared packages —

```
server             (Elysia 1.x, Drizzle, Postgres — Elysia already in place)
client             (Vite, React 18, Excalibur — regenerated lean, see below)
packages/protocol  (Zod discriminated unions for every WS message + REST DTO)
packages/world     (shared pure logic: grid math, A*, raycasts, chat propagation, check formulas)
```

**Stack verdicts (settled 2026-07-12).** Full-stack TypeScript stays: `packages/world` running identically on server and client is the load-bearing asset, and the game's low tick rate (one step per 2s, turn-based combat) makes Go/Rust/Elixir performance a solution without a problem. The realtime layer is **hand-rolled on plain `Bun.serve` WebSockets** — deliberately not Colyseus/Nakama: their value is synced shared state, while this game's defining mechanics (recognition, degraded chat, zone visibility) compute a **different view per recipient**; the seam where those frameworks fight you is exactly where this design lives. Elysia stays for REST/auth, keeping the existing bcrypt + httpOnly-cookie access/refresh JWT implementation (refresh-token-in-DB gives ban revocation); WS connections authenticate with the same cookie at upgrade — identity never rides the query string. ORM: **Drizzle replaces Prisma** — the schema is jsonb-heavy (levels, attributes, item effects, device graphs), and Drizzle gives typed jsonb columns, SQL-first migrations, and no codegen engine binary on Bun; the migration executes while the schema is still two tables, before the room engine lands. The client shell is **regenerated as a lean Vite app**: only the auth feature and api-client are ported; the inherited bulletproof-react scaffold is deleted wholesale. Client state: Zustand for game state, TanStack Query for REST; Eden treaty types REST end-to-end while `packages/protocol` owns every WS message.

**Rendering architecture: imperative Excalibur scene + React DOM UI.** The client already ships Excalibur 0.30 and no Pixi; we keep it — Excalibur bundles what the Pixi plan assembled from parts: `TileMap` layers (replacing `@pixi/tilemap`), Actors for tokens, a camera with follow/zoom, pointer input, the action queue for tweens, and `DisplayMode.FitContainer` for the letterboxed fixed-logical-resolution canvas. A `GameRenderer` class owns the `ex.Engine` and its scenes (tilemap layers, token Actors, effects); all UI chrome — chat dock, sheet, inventory, panels, editors — is React DOM around/over the canvas. Text-heavy interactive UI (this game's centerpiece is chat) belongs in DOM; no React binding wraps the engine — React never renders into the game loop (the old prototype's stale-closure workarounds are the symptom this avoids). Client state in Zustand stores; Excalibur subscribes, React hooks read. Step glides (Part III) map to the Actor action queue (`actions.easeTo` over ~300ms).

**The server is fully authoritative.** Clients send intents (`moveTo`, `chatSend`, `itemMove`…); the server validates, mutates, broadcasts facts. Stepped movement (Part III) eliminates any need for prediction/reconciliation netcode. All dice, checks, chat propagation, recognition resolution, and effect application are server-side.

**A uniform modifier/hook framework** underpins traits, item effects, drugs, and status effects: systems expose named extension points (`chat.range`, `recognition.check`, `vision.occlusion`, `check.roll`, `task.speed`, `move.cooldown`, …) resolved through a character's active modifier stack. New traits/effects register handlers against hooks; they never modify system code. The same handler-registry pattern recurs for puzzle devices (Part X) and trait tiers (Part VII) — it is the load-bearing extensibility decision of the whole design. Because Phases 1–3 already consume hooks (`move.cooldown`, `chat.range`, `recognition.check`), the **minimal resolver — `resolve(stack, hookKey, input)` in `packages/world` — lands in Phase 1**, so early systems register against it instead of hardcoding and being retrofitted; the full registries and trait pool arrive in Phase 5.

**UI shell.** The `/game` route composes: the Excalibur canvas centered (fixed logical resolution, letterboxed); the chat dock (draggable/resizable, position persisted to localStorage); the nearby-players panel (Part IV); a top status cluster (identity, credits, connection, clock); toggleable panels — stat sheet `C`, inventory `I`, location/world map `M`; an escape menu (settings, chat filters, keybinds, logout). Cyberpunk visual identity (dark UI, neon accents, restraint on scanlines/glow) via Tailwind theme tokens shared by the landing/login/character-select routes. All starter-template demo pages are deleted.

### Testing philosophy

**Every gameplay rule is a pure function before it is a feature.** Range math, attenuation, degradation, recognition scoring, check formulas, per-size collision, zone visibility, A* — all live in `packages/world` as deterministic functions of explicit inputs (no sockets, no DB, no clock). That makes the core of the game testable at unit speed, and it keeps the modifier/hook framework honest: a hook is testable as `resolve(stack, input) → output`. Three layers, deliberately pyramid-shaped:

1. **Unit (`bun test`, the bulk).** `packages/world`: exhaustive cases plus property-style checks where cheap (A* paths always walkable and connected; degradation monotonic with distance; attenuation order-independent along a ray). `packages/protocol`: every message schema round-trips and rejects malformed input — doubling as the ingress-security test.
2. **Server integration (medium).** Real WS clients against an in-process server + docker-compose test Postgres, scenario-style: join→step→chat→portal→(later) fight→die. Because per-recipient resolution is the core mechanic, **the core assertion helper is per-recipient** — `expectHears(A, msg)`, `expectHearsDegraded(B)`, `expectSilence(C)` — asserting on observable outbound messages, never server internals. Zone visibility, layout-memory invalidation on edit, and cross-floor attenuation get their scenarios here.
3. **E2E smoke (thin).** One Playwright flow: login → enter world → move → chat between two contexts. It catches wiring breaks, not gameplay bugs.

Working rules: each phase's **"Ends:" criterion becomes an automated scenario** where mechanically checkable — the two-browser manual loop (Part XIV) stays for *feel*, not correctness; tests ship with the phase, not after it — a system without its scenario isn't done; the inherited scaffold's component tests are deleted with the scaffold, and UI-component testing stays out of scope until the UI stabilizes (DOM chrome is cheap to fix, game rules aren't); **determinism hooks from day one** — injectable RNG (seeded in tests) and clock (task clocks, cooldowns, initiative are tested by advancing a fake timer, never by sleeping).

## Part II — World model

**Hierarchy: World map → Maps (= Rooms at runtime) → Levels → interior zones.** The world map is a coarse cell grid. Cities (founded by players — see Part X for founding tooling) occupy clusters of cells; each city district is an exterior **Map** connected to neighbors at its edges (walk off the edge, cross-fade to the matching cell). A Map owns ordered **Levels** (z: undercity/street/rooftops; a building's floors). Buildings are Maps entered via portals. A **Portal** links cell→cell across any level/map and covers doors, stairs, ladders, hatches; an **elevator** is a portal group (`elevatorGroupId`) opening a destination-picker panel. Sound crosses levels: **cross-floor acoustics** treat floors like walls — vertical attenuation by floor material, resolved by the same raycast — so a conversation is (muffled) audible through the ceiling. Sight does not cross levels (future designated exceptions: balconies, stairwells). Voice leaking *outside* a building is designed-in (a cross-Room relay at portals/exterior anchors) but implemented late.

**Level grid format** (jsonb on `MapLevel`): dimensions, tile size 48px; layers `floor`, `floor2`, `walls`, `objects`, `overhead`; collision derived from tile properties + overrides, **checked per size class** (S/M/L — a small-only duct is passable for S, wall for M/L); typed cell annotations: spawns, portal anchors, zones (named cell regions carrying visibility/lock/overlay semantics — see below), acoustic overrides, light hints, device anchors, resource nodes. Tile indices reference a **Tileset** registry (index → atlas frame, walkable, speed, **sound material** for chat attenuation). The existing 48×48 atlas (currently imgur-hotlinked from `client/src/components/game/assets/tileset.ts`) is vendored into `client/public/` and becomes tileset #1. Custom format over Tiled because maps live in the DB for live editing; a Tiled importer can come later.

**Rooms.** Each `(mapId, instanceId | null)` materializes server-side as a Room — **building-scoped**: a whole building with all its superposed levels, or one exterior district (`null` = the public world). Building scope is what lets acoustics cross floors and keeps a multi-storey scene one social space. The Room is the unit of interest management and chat; every outbound message is computed **per recipient** (identity labels, degradation, zone visibility). Lazy load on first entry, persist + unload when empty. A disconnected character lingers ~30s before `entityLeave`.

**Interior zones.** Within a building level, the map divides into zones — the "rooms" players speak of: named cell regions in the level JSON carrying **visibility, lock, and public/private semantics**. Stepping into a zone reveals its background and objects; unentered zones render **grey**. Characters you can see = everyone in your zone, plus anyone in an **unlocked/public zone in line of sight**. A character **remembers a zone's background layout** (never its objects) once they've been inside — persisted as `ZoneMemory (characterId, zoneId, levelVersion)`: any edit to the building/level bumps the level `version`, so the memory invalidates naturally and the zone greys out again. The client renders remembered backgrounds from its cached level data; the server never sends objects for unentered zones. **Full-wall overlays:** building owners may upload image overlays matching a zone's dimensions to replace the default wall/floor sprites — this rides the avatar-upload subsystem (size/format caps, re-encode, review queue) and is stored as a per-zone asset reference inside the level JSON, so it flows through versioning/revisions/hot-push like any other edit.

**Private instances.** An instance is a **forked Room**: a shadow copy of a whole building or district — every floor of the bank, since Rooms are building-scoped — with the same geometry but separate entity/chat space. Because all systems operate per-room, they inherit instancing for free — which is why the room key includes `instanceId` from day one even though the feature ships late. Triggers: **consensual scenes** (invite/accept → private fork of the current location, participants vanish from public); **event instances** (a trigger — vault device attacked, GM button — snapshots everyone inside the event zone at that moment, like the combat-zone capture rule, and spawns template NPCs: guards, employees); **GM-staged** events. No late entry by default — the entire point is that outsiders can't fly in when word spreads; a forced-breach option can be an event property later. The public copy shows a facade meanwhile: doors locked, optional leaked flavor (muffled alarms as sensory events), and it is locked against modification. On end (timer/objective), **merge-back per event template**: character-borne consequences (injuries, deaths, loot) always carry; world changes (blown vault, device states) persist or reset as configured. `EventTemplate { trigger, zone, npcs, duration, mergePolicy }`.

**Wilderness and procgen.** Outside cities, the world-cell grid is generated **on demand**: a cell's map is produced from the **resource layer** (per-cell authored scalar fields: danger, salvage density, ruin presence, …) plus a stable seed, then persisted as a normal `MapLevel` — generate once, stay consistent. Generation composes with **fixed content**: treasure-map loot, quest sites, and **player-buried stashes** (burying items at a coordinate and recovering them is a supported verb). POIs are hand-made, procgen, or both (Part X's dungeon editor decorates either).

**Transports.** A transport (bus/train/maglev) is itself a small interior Map with its own Room — a real RP space. A `TransportLine` is an ordered list of stops (portal anchors on maps) with travel times; a vehicle has a state machine (docked / in-transit with ETA); boarding is a portal in, and on arrival the exit portal re-targets to the destination stop. Long-distance travel between cities happens here; later flavor: breakdowns, checkpoints, robberies (as event instances).

## Part III — Movement

**All movement is stepped**, cell to cell, on a **step cooldown — default one move per 2 seconds out of combat**, a config value modified per context via the `move.cooldown` hook (roads, vehicles, encumbrance, traits; combat replaces it with the turn economy). Clicking a distant cell queues a path (shared A* from `packages/world`); the server advances one step per cooldown; click elsewhere to cancel. Each step renders as a **~300ms glide tween** — pure presentation so players can follow each other's direction of travel; authoritative position is always exactly one cell, keeping chat ranges, raycasts, and adjacency unambiguous. World-cell travel in the wilderness uses the same cadence concept per cell. Walking pace is deliberately uniform and social — not stat-scaled.

Protocol: `moveTo {x,y}` intent → server emits `entityStep { characterId, from, to, at }` per step. Room entry sends `roomSnapshot` (level JSON cached client-side by level `version` hash + entity list). Portals crossing a Room boundary (building ↔ street, map ↔ map) swap Rooms with a fade; intra-building portals (stairs, elevators) stay in the same building-scoped Room and just move the token across levels.

## Part IV — Identity, appearance, and presence

**Paper-doll appearance.** A character's observable appearance is their equipment on a default **silhouette determined by race and gender** (customizable within the template). Slot sets are data on the `Race` template — number and position vary by anatomy (four-armed races, tail slots); cyberware may later add slots. **Launch roster: the Shadowrun metatype spread** — Human, Elf, Dwarf, Ork, Troll — chosen to exercise the size system; a race defines a **size range, not a fixed size** (Dwarf: S/M; Troll: M/L; Human: S/M/L), and the character picks a size class within it at creation. The fantasy-in-cyberpunk direction also dovetails with the locked-attribute magic reveal planned for later (Part VII). Hovering/clicking a silhouette slot inspects that equipped item.

**Portrait avatar.** Priority: item override → player upload → `?` default. Masks/helmets carry their own portrait via item properties. Uploads are a real subsystem: size/format caps, server-side re-encode (strip metadata, normalize), volume/S3 storage, report + admin review queue.

**Recognition.** Every character has a `presentedName` (null by default → observers see a **descriptor** generated from visible equipment: "a figure in a sealed helmet"). A per-observer recognition check (Perception + Insight vs gear concealment + disguise skill, via the `recognition.check` hook — traits like "faces forget you" plug here) gates whether the presented name shows. One identity pipeline resolves the label used **everywhere**: nearby panel, chat attribution, token hover, examine. Future layer: per-observer memory/contact tags (recognize regulars regardless of presented names).

**Map tokens.** Players are circle tokens: base color (default blue; custom color shows **only to observers who recognize the wearer**), equipment-attached decorations (`tokenDecoration` item property: cat ears, visor line — always visible, they're physically worn), size-scaled (S/M/L). Hover resolves identity + portrait; click examines/targets.

**Nearby-players panel.** DOM window listing entities within perception range **in zones you can see** (your own zone plus unlocked/public zones in line of sight; raycast-filtered later): portrait + name-slot per the recognition rules.

**OOC forum.** The forum shipped in V0 is deliberately **out-of-character**: posts are attributed to the **account**, not a character, and it lives entirely outside the identity/recognition pipeline. An in-character counterpart — character-attributed boards whose authorship resolves through the same identity pipeline as chat (presented names, recognition, alt separation) — is planned but not yet designed (Phase 12+). It must be a separate surface, not a retrofit onto the OOC tables: account attribution links alts publicly, which is exactly what recognition exists to prevent.

## Part V — Chat (the centerpiece)

**Speech modes** (ranges in cells, Chebyshev): whisper `/w` = 1; murmur `/m` = 3; talk (default) = 10; yell `/y` = 25; scream `/s` = whole level. Effective per-listener distance = geometric distance + **wall attenuation from a Bresenham raycast** (each blocking tile adds penalty by its sound material; open doorway none, concrete lots; **floors count the same way**, which is how cross-level speech inside a building resolves — Part II) ± Perception/trait/equipment modifiers (`chat.range` hook). Beyond ~60% of effective range the server degrades text (distance-proportional word replacement with `…`); at the edge only `You hear someone yelling nearby.` + direction. A scream through a wall arrives as a muffled scream. Acoustic zone overrides survive for special cases (soundproof booth, loud-bar noise floor). Modes render distinctly in the log (whisper small/dim → scream bold/accented); degraded gaps faded. Speech bubbles above tokens; out-of-range whispers visible as `* * *` — you see *that* someone whispers.

**Messages are structured, not strings**: segments (text | entityRef | itemRef | rollResult) + effect tags. This buys the interactivity requirements: hovering a name in the log **highlights the token** on the map (entityRef); **drag-and-drop an item onto chat** to show it off (`attachments` validated for ownership → clickable item card, range-limited like speech); `/roll` embeds server-rolled dice. Effect tags in two families, both server-resolved: *sender-side transforms* rewrite the text itself (drunkenness hiccups/slurs — Body-resisted; jaw injury clips words) and *recipient-side conditions* resolve per listener at delivery (gunfire masks concurrent speech as `—…—` for anyone without ear-protection equipment). Separately, **sensory events** target the chat window itself: flashbang washes out/saturates affected clients' chat and screen (Perception cuts both ways — keen senses suffer more), EMP scrambles. The chat renderer is a component pipeline; every future system (combat, hacking, drugs, puzzles) plugs in by emitting tags/events.

RP staples from day one: `/me` action lines, `/ooc` or `(( ))`, `/roll`. Rate limiting (~5 msgs/4s) with mute escalation.

**Persistence is two tables** — what is per-recipient is the *perception* of a message, never the message itself. `ChatMessage`: one canonical row per utterance — sender character, room + instance, **building-relative coordinates `(x, y, z)`** (z = level index), mode, the full undegraded segments. This is the **hidden moderation/RP history**: deduplicated, complete even for messages nobody heard (a whisper in an empty room still logs — per-recipient-only storage would silently drop exactly what moderation most needs), with a longer GM-configurable retention. `ChatReception`: one slim row per actual listener — `messageId`, `characterId`, and the **perception delta**: the identity label that listener resolved at delivery and the degradation band. Recorded, not recomputed — once positions and recognition have moved on, what you perceived a week ago cannot be reconstructed. **Personal history:** each *character* (not account — alts don't share what they perceived) keeps the last **min(7 days, 20 messages)** of receptions, loaded into the chat dock on login; reception rows beyond the window are pruned lazily. Future long-range comms (contact-chip `/dm`, faction radio) ride the same pipeline via a `channel` field, designed in now.

## Part VI — Combat, death, and Limbo

**Turn-based with initiative-as-countdown, fought on the live map.** A combat instance = participants + a visible **zone** (union of radii around participants, recomputed as they move). Initiative derives from Agility onto **1–3 as a delay**: 1 acts after one turn, 3 after three, then a fixed rotation. Joiners — voluntary or **bystanders caught by the zone** — are flagged immediately and act after their initiative delay (high initiative = fast ambush response). A turn: movement (stat-budgeted cells), attack, item use, or disengagement; turn timer (~30–45s) auto-passes idlers. **Fleeing is spatial**: exit the zone using movement across one or more turns — the zone follows participants, so pursuers drag it along. Non-participants outside the zone live in normal time. Overlapping combats merge. Defeat = incapacitation/downed state. Checks: attack = d10 + Agility + weapon skill vs defense; damage from item effects.

**Size classes (S/M/L)** — chosen at creation within the race's size range (items/cyberware may shift later): token scale, per-size collision (small-only routes), and cover — the line-of-fire raycast treats a larger body between shooter and smaller target as cover. Size constrains equipment via item properties.

**Death & Limbo.** Death requires deliberately finishing a downed character (execution) or lethal hazards. The dead transfer to **Limbo** — a separate city cluster (Maps with a flag) where violence caps at incapacitation and the character remains fully playable (chat, RP, its own society over time). Respawn gates on conditions (baseline: an eligibility timer at a clone-vat facility; hooks allow alternate exits later). Player's choice at eligibility: **return immediately weakened** (decaying debuff via modifier framework, scaling with how early) **or linger and emerge fully healed**. **Killer trauma:** executing a player applies a stacking, slowly-decaying trauma status to the killer (exact penalties TBD: composure penalties, intrusive sensory events, reduced XP gain, a tell readable by high Perception) — death has weight for victim and aggressor; traits can dampen or amplify it.

## Part VII — Stats, progression, traits, accounts

**Four base attributes: Body, Agility, Perception, Logic.** (Presence rejected — social outcomes come only from what players say and do. Tech dissolved into skills. Nerve/composure starts as a derived resist, promotable to a full attribute later — the registry makes that trivial.)

- Body: HP, carry capacity, toxin/drug resistance, sustained physical labor (digging), forcing things.
- Agility: initiative, combat move budget, dodge, stealth, fine motor.
- Perception: recognition checks, effective hearing, exploration/spotting, ambush awareness; suffers sensory events harder.
- Logic: hacking/intrusion, ICE programming (crafting deployable defense programs — asymmetric PvP: your Logic's ICE vs their intrusion), engineering, medicine (with Agility component for surgery), decryption, analysis.

**Data-driven registries, not columns**: `AttributeDefinition` and `SkillDefinition` tables (id, name, linked attribute(s) + check formula, caps, creation cost, `locked` flag); characters store `attributes`/`skills` jsonb keyed by definition id. Sheet UI and check service render/resolve whatever exists. **Adding magic mid-game** = insert a locked `resonance` definition + skills + effect handlers; the sheet growing a new line is the reveal.

**Checks & tasks.** One formula server-side: d10 + attribute + skill vs difficulty/opposition (hookable at `check.roll` — "a little luckier" trait rerolls 1s). Long verbs (dig ruins, surgery, repair, ICE programming) are **task clocks**: total effort + tick interval; each tick while present and undisturbed rolls quietly, adds margin-based progress, occasionally throws complications. **Progress persists in the world** (half-dug pit in a persisted wasteland cell stays half-dug; a patient stays mid-surgery). Combat/leaving pauses the clock.

**Location history.** Places remember what happens in them: a single `LocationEvent` table — `{ mapId, instanceId?, x, y, z, kind (death | wound | bleed | drugUse | …extensible), actorCharacterId?, data jsonb, salience, timestamp }` — on the same building-relative coordinates as chat. Every system emits through one `emitLocationEvent()` call at its natural points (execution, downing, bleed ticks, drug consumption); the event vocabulary grows phase by phase exactly like hook registrations. Consumed by the **search/investigate verb**: a task-clock Perception/Logic check over a Chebyshev radius on the level, results filtered and ranked by **recency × salience** — and hookable at `search.location`, which is where traits extend it (blood-sense reads old bleed events; psychometry-style traits read further back in time). Because `ChatMessage` shares the coordinate scheme, what was *said* at a spot can join these queries later without schema change. Retention decays by salience — deaths linger for months, bleeding fades in days — GM-configurable.

**Progression.** Skills progress **by use** (grind), throttled per skill per day with diminishing returns to kill botting. Attributes rise **only at level-up**. **XP rewards all activity** — messages, movement, tasks, combat, digging — with server-side anti-abuse on the chat grant: entropy minimum, counting cooldown, more XP with players in earshot, hard hourly diminishing returns; goal: normal play levels you, nothing is worth farming.

**Accounts & creation.** An account holds several characters, **one active at a time** (single connected character; switch from character select, mild cooldown as a config knob). **One new character per account per 14 days** — the guard against trait-fishing and disposable alts. Creation: race + gender + size (within race range), point-buy attributes, and a draw of **3 random traits, rerollable a few times during creation** (keep the final set).

**Traits.** Each character starts with **3 random traits from a pool of ~100 level-1 traits**, each individually programmed as modifier-framework handlers (identity decay, carrying voice, wall-sight, minor luck…). Traits are **private** — on your own sheet only; others discover them through observation. Level-up grants an attribute point; trait advancement sits on top: **superior trait tiers are bespoke live-ops content**, earned via months of play or achievements, designed in dialogue with the player, implemented as new handler tiers. The hook framework is what keeps 100+ bespoke behaviors maintainable.

## Part VIII — Inventory & items

`ItemTemplate` catalog (name, description, icon, kind, stack rules, slots-occupied, equip-slot type, size restriction, **effects jsonb** — armor, damage, ear protection, concealment rating, `tokenDecoration`, portrait override) → `ItemInstance` (template ref, qty, durability/charges, instance meta, one location: character container / equip slot / ground / buried stash / trade escrow / world container). **Credits are a scalar on Character**, not an item. Equip slots come from the race template's slot set. Server-validated intents: `itemMove/Equip/Unequip/Drop/Use/Split/Pickup/Bury`. Ground items are room entities (despawn ~10min); **buried stashes persist** in world cells. UI: grid backpack + paper-doll equip panel (drag-drop, context menus, tooltips); drag onto chat = show-off. Trading (future, designed): adjacent-player two-pane escrow, atomic swap. Gear boosting/modification via Engineering task clocks with failure risk (Dreadcast-style).

## Part IX — Economy

**Player-run in the middle, city-AI at both ends.** The faucet: **scavenging and excavation** — digging ruins in wasteland cells (task clocks on procgen'd sites, yield scaled by the resource layer) and street-level scavenging in cities (low-yield respawning nodes: scrap piles, salvage points) produce **resource items** (scrap, components, chems, data shards — graded by quality), sold for credits at **public exchange structures**: city-AI-run counters (device annotations on maps) with dev/GM-set posted rates. Between faucet and drain, the economy is player-run — services, trade, shops, wages emerge from players, not NPCs.

**The main drain: Projects.** Players or groups petition the **core city AI** (in-fiction interface: a terminal device) to realize essentially anything — a bridge between districts, a new bar built out, a transport line, a feature — with prices set arbitrarily by devs/gamemasters. Flow: petition submitted for a **low fixed fee** → GM/dev reviews and **quotes** a realization price (credits and/or resource items) → petitioners **fund it over time** (a contribution ledger, multiple contributors) → on full funding the project is **delivered** as live-ops work (often a map edit, new device, or new content — frequently *built with the editors of Part X*). `Project` lifecycle: petitioned → quoted → funding → in-progress → delivered / rejected. This makes the biggest credit sink identical to the content-request pipeline, and gives GMs a price lever over the whole economy. Secondary drains: transport fares, clone/respawn fees, gear-boosting costs and failures, player-construction material costs (Part X), rent (with housing later).

## Part X — The editor ecosystem & admin tools

Three tiers of world-building tools, all operating on the same level-JSON format and the same renderer (edit modes of the live client, UI in React DOM), differing in **audience, scope, and constraints**. All editing writes through the same pipeline: save jsonb → bump level `version` → record a `MapLevelRevision` (revert is one action) → hot-push `levelUpdate` to the live room. The V0 editor (`client/src/app/routes/app/editor.tsx` — DOM-grid, Admin-gated, already saving through this pipeline; the broken legacy `MapEditor.tsx` was deleted) seeds the common core: tile palette from tileset atlases, paint/fill/eyedropper per layer, collision and spawn paint (size-class paint and annotation placement still to come).

**Tier 1 — GM world editor (design new cities).** Operates at world-map scale, GM/admin role only: paint the **resource layer** fields across world cells; found or place **cities** — lay out a city as a cluster of district Maps, define their edge connections, set spawn districts; place and route **transport lines** (stops, travel times, vehicle interiors); place world-level POIs and `FixedContent` (treasure sites, quest locations); tune and preview **procgen parameters** per biome/cell with a seeded preview before committing generation. City templates (a starter district scaffold) make founding fast. This is also the tool that *delivers* city-founding Projects when players fund them.

**Tier 2 — Player building editor (design buildings).** Players design the interiors (and within limits, structure) of buildings they own — obtained via housing, city founding, or funded Projects. Same editing core, heavily sandboxed: the **footprint and exits are fixed** by the plot; the palette is a **whitelisted furniture/tile set** (no spawn points, no arbitrary portals, no editing outside the plot); validation runs at save (connectivity — every walkable cell reachable from an exit; at least one M-size route to every room; portal integrity). Construction has **material costs** — tiles and furniture consume resource items/credits, making player building a proper economy sink — and edits can optionally flag the building "under renovation" while applied. A GM review flag exists per city (auto-publish vs. approval queue) so communities can choose their moderation posture. Owners can grant co-editing rights (roommates, company staff).

**Tier 3 — GM dungeon/POI editor.** A superset of the map editor for authoring adventure content, targeting POIs, dungeons, and event sites: everything from Tier 1/2 plus **spawn tables** (enemies by danger rating), **loot placement** (FixedContent + container seeding), **event templates** (the instancing system's NPC rosters, zones, durations, merge policies — Part II), and the **puzzle framework**:

Puzzles are built from **devices wired into trigger→condition→effect graphs**. Device types at launch: **prompt enigmas** (a terminal poses a riddle; players type an answer — normalized/fuzzy matching, attempt limits, lockout timers); **keypads/passwords** (exact codes, learnable through play — found on a note item, overheard in chat, extracted from a hacked device); **locks** (key items or Lockpicking/Intrusion checks); **switch sequences** and **pressure plates** (size-class-sensitive — a puzzle only a Small character can thread, or that needs a Troll standing on a plate); **timed doors**; **hack nodes** (Logic/ICE interactions). Effects: open/close/toggle devices, spawn entities, reveal hidden annotations, teleport, emit sensory events, grant loot, advance an event objective. Conditions compose (AND/OR, ordered sequences, state machines), and the whole thing is a handler registry — like traits, **new puzzle mechanics are new handlers**, not engine changes, which is how "other puzzles to be determined" stays cheap forever. The editor presents devices as placeable annotations with configuration forms and a visual link mode (draw wires between devices). Dungeons decorate both hand-made maps and procgen output.

**Moderation & ops kit** (GM/admin roles): teleport self/others, kick, mute (feeds the chat rate-limiter), announcements, chat-log queries over `ChatMessage`, avatar review queue, Project pipeline management (quote/track/deliver), trait live-ops tooling (grant superior tiers), instance monitoring (peek/join/terminate), economy dashboards (faucet/sink flows, exchange volumes).
